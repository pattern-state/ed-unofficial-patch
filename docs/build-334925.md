## What changed in the game

Elite updated on 2026-10-23 from build 334473 (PE stamp `0x6ACD513D`, SHA-256
`6891f70a…`) to build 334925 (`0x6ADA8048` = 1792704584, SHA-256
`ed5a8f8c…e264b63`; Steam `VersionInfo.txt` 2026.10.23.334925). The image size
is the same, `0x640C000`, and the seven sections keep their virtual addresses.
`.text` shrank by `0x160` (virtual size `0x4DB4AEE` → `0x4DB498E`, raw size
`0x4DB4C00` → `0x4DB4A00`), `.rdata` by `0x20`, `.pdata` by `0x6C`, `.reloc` by
`0x18`; `.data`, `_RDATA` and `.rsrc` are the same size. The three executables
are kept in the main checkout's `analysis/` (`EliteDangerous64.exe` 332841,
`-334473.exe`, `-334925.exe`).

## How the move was measured

`tools/build_diff.py map`, the method `docs/build-334473.md` describes, over
222 distinct addresses: the 213 that the 334473 retarget carried plus the 16
render pipeline seed targets (7 are in both). Result:

| | same RVA | moved | changed | unmapped |
|---|---|---|---|---|
| code, 180 | 1 | 179 | 0 | 0 |
| data, 42 | 19 | 23 | 0 | 0 |

Of the 180 code addresses, 54 are IDENTICAL bytes at the new address and 126
are RELOC-ONLY (every differing byte is a rel32, RIP-relative or image-base
displacement that lands on the mapped counterpart of its target). Data: 35
XREF-EXACT, 7 XREF-BRACKET. The code moved by `-0x30` to `-0x120` (most
`-0xA0` or `-0x60`); .data by 0 for the light grid and Explorer Cam globals,
`-0x30` or `-0x40` for the vtables and name literals. A further 232 addresses
that the old inventory never listed were mapped the same way
(`.agents/build-334925/map_extra.json`): `mem_tick.cpp`'s 18 byte pins and 3
data globals (added after the 334473 retarget), the CPU profiler's class
tables, the rigs' layouts and the comment citations.

Not addresses, but build facts that moved with the file: the Oculus profile
floors `.text`'s span at `0x4DB4A00` (the 334473 value `0x4DB4C00` would have
refused 334925), two derived constants in `kinematic_eval_hook.cpp`
(`base + 0x43513A5`, the end of the list-merge hook site, and the part-test
return `0x42B77B6`), and the installer's qualified-SHA pin.

## FSR4 live quality (2026-11-25)

`src/d3d11/game_render_scale_pins.h` admits only timestamp `0x6ADA8048`,
image size `0x640C000`, and independently checked instructions and pointers.
The archived executable SHA-256 is
`ed5a8f8cd10f9a80d3bda5badd7ba1d4fcfc15996c8c7e018852cb170e264b63`.

| Witness | Build 334925 meaning |
|---|---|
| Registration initializer at `0xD3B50`; table at `0x52EA470` | Registers wrapper `0x27BE470`, which recovers the renderer and tail-calls requester `0x2889940`. |
| Requester at `0x2889940`; context read at `0x2889A4D` | The callback runs on the game's requester thread and uses the current renderer's context at renderer+`0x1180`. |
| Dirty/configure block at `0x288A0F2` | Renderer+`0x10C8` requests the game's normal configure/rebuild path. |
| Flat SS setter at `0x2878D40` | Context+`0x3564` is SS; context+`0x3568` and +`0x356C` are minimum and maximum. Requests outside valid live bounds refuse before writing. |
| Settings copy at `0x281E678` | Context+`0x33D0` is copied from settings+`0x30`; the existing SS-hold mode predicate owns interpretation. Context+`0x2AE0` is a separate flag and is not the mode. |
| HMD configure path at `0x281835A` | Context+`0x3558` is HMD scale. Renderer+`0xE58` is its manager; renderer+`0x1188` is settings. |
| Manager alias at `0x284F4A8` | Settings+`0x7D0` names the renderer's manager. |
| Manager vtable at `0x512B278`; setter/getter at `0x8D34E0` / `0x8D2A20` | Slots +`0x100` / +`0x108` operate on manager+`0x4E4`. Context and manager HMD values have independent checked targets and receipts. |

Retarget by following the registration initializer's stored pointer, the
wrapper's renderer adjustment and tail jump, then the requester's context and
dirty/configure accesses. Re-derive the settings-mode copy, SS clamp,
manager aliases and vtable accessors from that build's executable. Matching
field numbers alone does not admit another build. No executable or decompiled
code is redistributed.

The bridge preserves flags before stack arithmetic, volatile integer state,
x87/SSE/MXCSR, nonvolatile registers through the Windows ABI, stack arguments
and original return. Windows unwind metadata describes its frame. A nearby
absolute-jump relay handles arbitrary DLL distance without weakening
CodeHook's rel32 refusal. Prepare publishes the original before the entry
patch. Successful hook, relay and forwarding storage remain process-retained;
shutdown closes callback admission while original forwarding remains valid.
Installation requires the production graphics-module pin receipt.

Native Windows CPU validation used the isolated `t04` snapshot under
`C:\Dev\EDUP-Validation\fsr4-quality-2026-11-25` with MSVC and the Windows SDK
selected by `edup-native-env.cmd`. The initial ABI run refused a replacement
more than 2 GiB from the requester. After adding the relay, the real CodeHook
and assembly bridge pass the binding, ABI, unwind, recursion and retained
shutdown tests. This is CPU evidence; no Elite launch, game-field acceptance
or GPU execution is claimed. Full candidate validation remains a separate gate.

The canonical `tools/hook_signatures.py` audit registers exactly
`game_render_scale_pins.h` and `game_render_scale_binding.cpp` in its reviewed
`AUDIT_EXACT_ONLY` family registry. This preserves the adapter's approved
334925-only support: the facade requires `gameBuildKnown()`, while the external
binding independently rejects a different PE identity or any failed instruction,
registration, vtable or object-ownership witness. Whole-function relocation
alone cannot prove these field layouts. No address is classified as a
non-address, and no unknown-build resolver support is added. Owner self-tests
retain rejection of similarly named future files and of raw address use by a
consumer outside these two files.

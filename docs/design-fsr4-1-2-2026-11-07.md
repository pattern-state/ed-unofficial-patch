## 1. Intent

Give Elite Dangerous a proper AMD FSR 4.1.2 integration of the kind a current AAA patch ships: FSR 4 upscaling with the standard quality modes, AMD frame generation, clean edges without the game's broken anti-aliasing and end-of-chain sharpen, and a user-facing way to choose the mode. Flat screen and VR, Linux (Proton) and Windows.

**Why now.** Elite's engine has had no upscaling work in years; it ships FSR 1 and an anti-aliasing path that most players turn off, running 2x supersampling instead to get a clean image. At flat ultrawide resolutions that is expensive; in VR, where two high-resolution eyes are rendered, it is crippling. A 9070 XT / 9800X3D / 64 GB machine is a common configuration today and the game does not use it. Frontier has given the community modding effort its blessing.

**Why ED-UP, not our own mod.** Sean's ED-UP (`ed-unofficial-patch`, formerly `edvr-unofficial-patch`) already owns everything this needs except FSR 4 itself: the D3D11 proxy with device, swapchain and Present hooks; camera and projection hooks that already apply jitter; motion vectors with per-object engine velocity; the HDR tone-pass route on flat; depth and UI separation; DLSS, FSR 3.1 and XeSS as switchable engines; an in-game settings panel; an installer with a settings window; a Linux installer; Windows CI builds; a release process; and a field of users. It also holds a 5,000-line FSR 4 branch that already ran FSR 4.1.1 under Proton. Our previous plan was re-deriving large parts of that from scratch. Sean has agreed that David and Claude own the FSR 4 work.

## 2. What exists today (facts, read 7 November 2026)

**ED-UP main** (`4aeb712e`, 7 Nov): engines `fix.temporal_aa = off | on | dlss | fsr | xess`; flat render scale is Elite's own Supersampling setting (`SSAAMultiplier` in the user's `Custom.<major>.<minor>.fxcfg`), which ED-UP reads but never writes; the F8 panel's Performance tab holds the engine row; the installer's settings window edits `edvr.ini` / `edvr-flat.ini`; a standalone launcher is designed (`docs/design-launcher-2026-11-07.md`), nothing built, with "the settings table as data" at step 7 and Linux at step 8. Release candidates `v0.22.0-rc.1` to `rc.7` are all on main. No `fsr4` code is on main.

**The FSR 4 branch** `claude/fsr-4-1-flat-vr-support-5f6ea4` (Sean with Claude, 23–24 Oct): 13 commits, 43 files, +5,008 lines. A fourth engine `src/d3d11/fsr4_engine.{h,cpp}` behind `EDVR_HAVE_FSR4`, one context per upscaler slot (eyes 0 and 1, VR world route 2, flat 0), over a D3D11/D3D12 bridge copied from the XeSS engine: D3D12 device on the game's adapter, keyed-mutex shared textures, shared fence, allocator ring. `fix.temporal_aa = fsr4`, flat and VR. `tools/fetch_fsr4.py` pins FidelityFX SDK v2.3.0 (FSR 4.1.1, `amd_fidelityfx_upscaler_dx12.dll` 4.1.1.2740) by SHA-256. Flown flat on Sean's Strix Halo under Proton: every dispatch clean, live engine switches clean, jitter live; the keyed-mutex release stall (5–7 ms a frame under DXVK) was found and fixed by holding the keys for a context's life (evaluate 6.6 → 0.27 ms, 60 fps cap reached). Unfinished: Sean saw vertical streaks in a station (never compared against FSR 3); VR never flown; the AMD licence never read; not merged, by Sean's rule (branch decision D9).

**Merge state:** the branch is based on main of 23 Oct; main is 1,224 commits ahead. A trial merge onto today's main conflicts only in `AGENTS.md`, `build.bat` and `docs/building.md`. Every engine integration point (`temporal_pass.cpp`, `native_temporal.cpp`, `flat_mono_resolve.cpp`, `temporal_mode.h`, `menu.cpp`) auto-merges.

**AMD SDK 2.4** (`reference-projects/FidelityFX-SDK-2.4`, commit `7539ae8b`): `amd_fidelityfx_upscaler_dx12.dll` 4.1.2.4555; `amd_fidelityfx_framegeneration_dx12.dll` 4.0.2.4555; loader 2.4. Our earlier contract review found the 4.1.1 → 4.1.2 upscaler API delta is the version constant and a comment: no contract change. Frame Generation 4.0.2 requires an RX 9000-series GPU, D3D12 with SM 6.6, a mandatory call order (prepare → dispatch), camera position/up/right/forward each frame, and it can be dispatched by the application and presented through the application's own swapchain (it then forgoes AMD's driver-assisted pacing). `docs/license.md` grants binary-only redistribution of the signed DLLs with the notice reproduced, and forbids reverse engineering. That resolves the branch's open licence question (D8).

**Proton:** Proton Experimental (`experimental-11.0-20261027b`) bundles `amdxcffx64.dll` 2.3.0.2913 (the 4.1.1-era driver-side provider) behind `FSR4_UPGRADE=1`. Our own probe needed `FSR4_UPGRADE=1` to be offered any 4.x provider. Which provider actually serves when a 4.1.2 DLL is shipped beside the game and the shim is also present is not established.

**Our repository (`ed-fsr4`)** keeps: the isolated development copy of the game on the second NVMe with its own Proton prefix and Frontier profile; `tools/launch_frontier.py` with staging receipts and restore-on-exit; `tools/run_probe.py` (an FSR 4 probe under Proton, in its own prefix); `tools/benchmark_native_hdr.py`; keyboard-driven menu, galaxy-map, panel and headlook automation from the game's bindings; OCR of the stock menu; graphics-settings reading. None of our `src/` rendering code carries over.

## 3. Goals

- G1. FSR 4.1.2 upscaling as ED-UP's `fsr4` engine, flat and VR, on Linux and Windows, with the provider pinned to 4.1.2 and proven in the log.
- G2. The standard quality modes as one user choice: Native AA (1.0), Quality (0.67), Balanced (0.59), Performance (0.5), Ultra Performance (0.33), expressed through Elite's own Supersampling value plus the engine row.
- G3. AMD Frame Generation 4.0.2 on flat, on RX 9000-series GPUs, doubling the presented frame rate with pacing that does not stutter, on Proton first (David's decision: try Linux, with Windows on the same hardware as the fallback, see D11). Frame generation in VR is not ours (see D7).
- G4. A clean image: Elite's own AA off (the user's setting, as for every ED-UP engine) and the game's sharpen not applied to the upscaled frame (ED-UP takes the frame at the tone pass before the game's final copy, so this is inherited by `fsr4`; PR 1 verifies it rather than builds it); no new shimmer, ghosting, HUD smearing or cockpit artefacts against the FSR 3.1 and DLSS baselines; the "vertical streaks" report resolved either way.
- G5. Mode selection in the places ED-UP users already look: the F8 panel, the installer's settings window, and Sean's launcher when it exists, all driven by the same settings table, with no hand-editing of ini or fxcfg files.
- G6. Shipped through ED-UP: installer payload, licence notice, release notes, and Sean's merge. Linux installer parity.
- G7. Every claim backed by a flight log, a benchmark or a capture; the same evidence discipline ED-UP already runs.

## 4. Non-goals

- A separate mod, launcher or DLL of our own. Everything user-facing lands in ED-UP.
- Frame generation on GPUs AMD does not support for it (RDNA 3 and older, NVIDIA, Intel). Upscaling with FSR 4.1.2 on RDNA 3 (INT8) is in scope; FG is not.
- Frame generation in VR. Sean's extrapolation design (`docs/design-frame-generation-2026-10-26.md`) is the VR route: it adds no latency, and we agree with its argument against interpolation in a headset. Nothing in this work touches the XR frame loop.
- Changing ED-UP's existing DLSS, FSR 3.1 or XeSS behaviour.
- On-foot VR, native OpenXR runtime work, headset-specific fixes: Sean's domain, untouched.
- Replacing ED-UP's bridge, settings system or installer. We extend them.
- Any write to the live Steam Elite install on David's machine during development; our isolated development copy only.

**Anti-goals** (would make it a failure even if it works): a build that only works with `FSR4_UPGRADE=1` and silently runs 4.1.1 while reporting 4.1.2; a quality mode that writes Elite's settings without telling the user or without restoring them; frame generation that looks fine in a screenshot and stutters in play; a PR Sean cannot merge because it breaks his rules, his CI or his flat/VR users.

## 5. Constraints

- **ED-UP's working rules** (`AGENTS.md`, `docs/building.md`): contributions by pull request; C++ changes need the full native Windows CI build (the `release.yml` workflow runs on every PR); on Linux, `tools/linux_toolchain.py build-dlls` gives compile-only builds for test flights, not validated builds; installs go through `tools/install_edvr.py`, logs through `tools/edvr_log.py`; every tool has `--self-test`; investigation docs carry a `## Status` block; the expensive resource is test flights.
- **Development on Linux** (David's machine: openSUSE Tumbleweed, 9070 XT, KDE Wayland, Proton Experimental). Windows is for testing, not development. The Wine toolchain needs a Visual Studio licence; David has one.
- **Test rigs:** Linux flat (David, 9070 XT, 5120x1440); Windows flat on the same machine, dual-booted from a new NVMe in the spare slot (drive and install pending as of 2026-11-08; same hardware, different OS, so Linux-versus-Windows comparisons are clean); VR on Windows over SteamVR with the Apple Vision Pro, which already runs ED-UP today (David), and a Quest 3 512 GB over Virtual Desktop (in hand as of 2026-11-08; Sean's headset, so results compare); Sean's own flights for his rigs. VR is therefore David's parallel track, not a dependency on Sean's schedule. Frame generation can only be tested on an RX 9000-series card.
- **Evidence:** ED-UP's flight-log discipline plus our benchmark and capture tooling. No claim without a log, a number or an image.
- **Licence:** AMD's binary redistribution terms are honoured by shipping the notice; no decompilation of AMD DLLs.
- **Authority:** no commit to ED-UP main; PRs only, Sean merges. No change to David's live Steam install.

## 6. Decisions

- **D1. Branch strategy: new branch off current ED-UP main, merge the FSR 4 branch into it.** Not continuing on the stale branch head, not starting from RC4 (older than main; Sean merges to main; RC7 is on main). The three conflicts are build scripting and docs. Rewriting would re-learn the keyed-mutex stall and lose 5,000 flown lines.
- **D2. Pin SDK 2.4: upscaler 4.1.2.4555 and frame generation 4.0.2.4555**, via `fetch_fsr4.py`'s SHA-256 pins. The provider is selected by its version id, not "latest 4.x". The log prints the full list AMD offers and the one chosen; a build that cannot get 4.1.2 refuses `fsr4` with the list in the refusal, as the branch's D7 already does for 3.1.5.
- **D3. The Proton provider question is answered first, with our probe.** Before any engine work: ship the 2.4 DLLs beside the probe, run with and without `FSR4_UPGRADE=1`, read the offered versions and the served one. The outcome decides whether users on Proton need the launch option and whether the shim can shadow the shipped DLL. Policy whatever the outcome (my call): `fsr4` runs on any 4.1.x provider but every label (log, F8 row, perf tile, release notes) names the version actually served and its source ("fsr 4.1.2" or "fsr 4.1.1, Proton driver provider"); it never says 4.1.2 unless 4.1.2 is served; and if the shipped 4.1.2 can be selected by version id alongside the shim's 4.1.1, it is.
- **D4. Quality modes are Elite's Supersampling value.** Built behind a key, default off, so the engine-row-only variant ships if Sean declines the write (my call: the writer is not speculative work, it is the same PR with the key flipped by his answer). ED-UP reads the real render size; the modes map to `SSAAMultiplier` 1.0 / 0.67 / 0.59 / 0.5 / 0.33 (AMD's ratios 1.0, 1.5, 1.7, 2.0, 3.0). Mode selection writes two things: the engine row in `edvr-flat.ini` (or `edvr.ini` for VR) and the supersampling value in Elite's active `Custom.<major>.<minor>.fxcfg`, using ED-UP's existing reader of that folder (`flat_elite_settings.h`) extended with a writer. The writer backs the file up first, writes only that one value, restores on uninstall, and refuses when the preset is not Custom or the file is unreadable. Elite reads the file at launch, so the row is marked `restart`. In VR the render size is HMD Quality, which ED-UP already handles; the VR quality row maps to that value by the same ratios. This is a decision Sean must agree to before it ships (his launcher design writes Elite's settings only for Epic); the F8 and installer rows can ship first with the engine row alone and the supersampling hint as text.
- **D5. One settings table, three surfaces.** New keys follow ED-UP's `edvr.ini` `# ui:` convention so the generated schema puts them on the F8 panel, in the installer's settings window and, when it exists, in Sean's launcher without separate UI work. We do not build a sidecar app of our own. If the launcher's Linux step is late, Linux users have the F8 panel and the installer under Proton, as today.
- **D6. Frame generation on flat: AMD FG 4.0.2 dispatched by ED-UP, presented through Elite's swapchain in ED-UP's existing Present hook.** AMD's own FrameInterpolationSwapChain is D3D12 and cannot wrap Elite's D3D11 swapchain, so the bridge runs prepare and dispatch on the D3D12 side with the upscaler's depth, motion vectors and camera, and the Present hook presents the interpolated frame then the real one with ED-UP's own pacing. Driver-assisted pacing is forgone. HUD handling uses the HUDLess input: the frame before ED-UP's UI composite where the route exposes one, otherwise the UI-doubling risk is measured and the mode refuses. Feasibility gate before anything depends on it: a flat flight at a fixed spot showing 2x presented frames, pacing within budget, no UI doubling, and the mandatory call order honoured. **This re-opens the "frame generation in the flat profile" entry Sean declined on 2026-10-27** (`docs/design-frame-generation-2026-10-26.md`, Declined). His reasons were that no vendor SDK has a D3D11 path, that flat's slow cases are ED-UP's own render cost, and that the users who want it most sit under AMD's 60 fps input floor; his re-open condition was treated flat frames at 60 fps or more on 120 Hz or faster displays. The bridge is the D3D11 path, and that condition names exactly the user this targets: an RX 9000 card that already clears 60 fps and wants its 120 Hz or 240 Hz display filled. It is our call to build it; PR 3 carries the gate's numbers as the case for merging it. **The user's switch and a measured gate coexist.** The user chooses frame generation on or off, as they choose a quality mode; while it is on, a per-frame gate decides whether a frame is generated and the F8 row says why when it is not: maps and menus (no motion vectors), rendered rate under AMD's 60 fps input floor over the last second, a pending resize, a history reset. Off is the default, so Sean's other users pay nothing for it.
- **D7. Frame generation in VR is out of scope (decided 2026-11-08).** Sean's design declines interpolation in the headset for its latency, and we agree: a frame held back is felt in VR in a way it is not on a monitor. The VR route is his extrapolation design, built on ED-UP's own depth and motion vectors with no added latency, and it is his to build. FSR 4.1.2 upscaling in VR stays in scope (G1); AMD frame generation does not enter the XR frame loop in this work. The flat FG engine (Phase 4) exposes nothing VR-specific and promises nothing to a future VR route.
- **D8. The image gate is comparative, with numbers.** `fsr4` is judged against `fsr` (3.1) and, on Windows, `dlss` at the same spots with ED-UP's F7 comparison key, in the log and by eye, flat and VR. The station streak report is reproduced or closed with evidence. Thresholds (my call; David may tighten): no artefact class visible under `fsr4` that is absent under `fsr` at the same spot; frame time at the same render size within 10% of `fsr`'s; ED-UP's price line for `fsr4` at or below `fsr`'s on the 9070 XT. Frame generation, flat: presented frames at least 1.9x rendered over a 30 s window at a fixed spot; p99 of presented-frame intervals within 25% of the mean; added latency at most one rendered frame (measured from the Present hook's timestamps); zero UI doubling in captures; AMD's mandatory call order verified by log. A gate that fails twice on the same cause with no new hypothesis stops the track and the plan is revisited.
- **D9. Our repository is the Linux harness.** `ed-fsr4` keeps the isolated game copy, launch/restore receipts, probe, benchmark and automation, and gains an ED-UP install path into that copy (through `install_edvr.py`, never by hand). No rendering code is kept.
- **D11. Frame generation is attempted on Proton first.** The D6 gate runs on Linux. If it fails on a cause that is Proton's (DXVK presentation, vkd3d-proton, the shim) and not ours, the plan's next step is installing Windows on the new NVMe in the same machine (the drive the dual boot lives on; the development game stays on its own volume) and running the same gate there; that install is a named task, not an improvisation. Windows-only FG is an acceptable shipped outcome only after the Proton attempt has a recorded cause. The same dual boot serves the Windows flat and VR flights.
- **D10. Delivery in merge-sized PRs, in this order:** 4.1.2 engine flat (Linux, then Windows); VR; quality modes and settings; frame generation flat; licence, installer and docs can ride with the first PR that ships DLLs. Each PR carries its flights, in ED-UP's format.

## 7. What is left to the builder

- The exact shape of the supersampling writer and its restore path (D4), including Linux paths under the Proton prefix.
- Pacing design for D6 (thread, timing source, VRR behaviour under DXVK), and whether DXVK's presentation model needs the interpolated present on a separate thread.
- Where HUDLess colour comes from on the flat HDR route and the LDR route.
- The phase count and jitter sequence at each quality ratio (ED-UP uses 8 phases at 1:1; AMD's query gives ceil(8 n²)).
- Reactive and transparency masks: optional in FSR 4; ED-UP has a UI/mover mask. Try on and off; keep what measures better.
- Sharpness: ED-UP's RCAS row stays the one sharpen; FSR 4's own sharpening stays off unless a comparison says otherwise.
- The flight matrix and benchmark scenes (reuse ED-UP's and ours).

## 8. Risks

| Risk | Consequence | Handling |
|---|---|---|
| Proton's shim serves 4.1.1 over the shipped 4.1.2 | Users get 4.1.1 while the UI says 4.1.2 | D3 first; refuse or label correctly |
| FG pacing without AMD's swapchain stutters | FG unusable on flat | D6 gate; measure before building on it |
| Sean holds his 2026-10-27 decision against flat FG | PR 3 not merged | D6: the PR is the re-open case, argued with the gate's numbers; FG is behind a key, default off, so it costs his other users nothing |
| Elite settings write breaks a user's preset | Support burden for Sean | Backup, one value, restore, refuse on anything odd; Sean's say |
| The station streaks are FSR 4's | Image gate fails | Compare against fsr/dlss; reactive mask and HUDLess variations |
| Main keeps moving under the branch | Merge churn | Small PRs, rebase often, Sean's RC cadence |
| Only one FG-capable GPU in the project | Thin FG evidence | Say so in the PR; Sean's users with RX 9000 cards as testers |
| FG fails on Proton for a Proton cause | Linux users get no FG | D11: Windows dual boot on the same hardware; honest release notes |

## 9. Success

A user on Linux or Windows installs an ED-UP release, picks "FSR 4 — Quality" and "Frame generation: on" in the F8 panel, installer or launcher, launches Elite, and sees a clean, stable image at a higher frame rate than native, with the log naming `fsr 4.1.2` and the provider list; in a headset the same upscaled image without frame generation. Sean has merged it and listed it in a release.

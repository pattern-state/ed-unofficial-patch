Windows and Quest 3 FSR 4.1.2 baseline — 25 November 2026

Status

fsr4-1-2 preserves the source used for the successful Windows flights.
fsr4-1-1 preserves later experiments awaiting Flight B validation.
Both branches pin AMD SDK 2.4 and prefer the 4.1.2 provider. The historical
4.1.1 branch name refers to the provider available during Proton testing.

Observed flights

Windows 11 Pro, Ryzen 7 9800X3D, Radeon RX 9070 XT.
Samsung Q9 OLED as reported by David, 5120x1440 output, 144 Hz.
Quest 3 through Steam Link and SteamVR OpenXR, 90 Hz.

Flat FSR 4.1.2 dispatched 3840x1080 -> 5120x1440 with Elite AA off.
David reported regularly above 130 FPS in flight and roughly 120 +/-5 on foot.
VR FSR 4.1.2 dispatched both eyes at 2528x2704 -> 2528x2704 (Native AA).
David found the image very good and the flight comfortable.

Earlier driver 32.0.31044.16 gave 52.8 application FPS over 330 seconds of
focused VR rendering. After Adrenalin 26.11.2 / 32.0.32029.2010, the flight
averaged 72.8 FPS across eight minutes, with 30-second averages of 54.0–82.3.
Docked rendering at Cheranovsky City averaged about 40 FPS for two minutes.
Routes and views differed between runs, so these figures do not isolate a
driver improvement. Headset refresh and application FPS are distinct measures.

Changing Elite Supersampling to 0.5 was held at 1.0 by the VR gate.
Reduced-resolution VR remains untested. HMD Image Quality controls that input.
Frame generation remains untested.

Value in fsr4-1-1 at f36e3893

AMD's SDK sample. This is a justified candidate for targeted validation.

registration and AMD input checking. These provide useful investigation tools.
The longer FSR jitter experiment was reverted after a large FPS loss.

The Flight B checklist is open. These later rendering changes were absent
from the successful Windows baseline.

Relationship to upstream

Upstream main 494b4ed014f2370ed01719d8158a45e1a88d097d pins the same two AMD
runtime DLL hashes as this baseline. Both use a D3D11-to-D3D12 shared-resource
bridge and AMD ffxDispatch. DittoSR is a separate option.
Main chooses the highest provider with major >=4. This branch prefers 4.1.2.
Main adds direct shared views to flat_mono_resolve and improves queue ordering
and teardown. The VR on-foot world route also calls flat_mono_resolve.
Cockpit-eye temporal_pass calls still use the bridge's copy path.
Main also fixes context release on leaving FSR4 in the VR world route.
Main has not been compared in matched flights on this machine.

The fork's provider menu diagnostics remain useful, with one caveat:
fsr4ServedLabel infers 'driver provider' from a version mismatch. That does
not independently establish where the provider binary came from. A future
diagnostics change should distinguish observed version from inferred origin.

# FSR 4 (4.1.1) iteration plan

**Goal:** improve what `fsr4` feeds AMD's runtime, and add a quality row, before PR 1 to Sean.

**Branch:** `fsr4-1-1`. Later merged into `fsr4-1-2`; merges go that way only.

**Source:** the read-only review of 2026-11-09, made against FidelityFX SDK 2.4's headers, docs and sample. Finding ids (C1–C7, P1–P5) are the review's. The review lives in the session scratch. Its findings are restated here so this plan stands alone.

**Evidence:** [docs/investigation-fsr4-2026-11-08.md](../docs/investigation-fsr4-2026-11-08.md).

## Global constraints

- Agents never push. David pushes by hand.
- Commits use `git commit -F <file>`. Flown commits are never rewritten: merge, never rebase.
- Test first: the failing rig case comes before the code. Rigs run in Windows CI on push. Locally, `linux_toolchain.py build-dlls` in the podman container proves only that the code compiles.
- Flights use the isolated development game only, never the Steam install. Announce a rendering change before flying it.
- No mocks of application code. Rig cases call the real header functions.
- Docs in terse UK English.
- Changes touching code Sean shares across engines (the finish shader, mip bias) say so in the PR body as separate items he can accept or decline. Applying the jitter policy to `fsr` is offered to Sean as a separate item, not done here.

## What we know (from the review and the logs)

- 4.1.1 reports `required=0xF optional=0x30`. It consumes reactive and transparency/composition masks if they are given.
- The bridge costs about 0.2–0.4 ms GPU and 0.06 ms CPU per frame. The fps spread across Supersampling levels is scene cost. No performance work in this plan.
- Already right: the create chain and provider check, depth and motion-vector flags, MV scale, preExposure, reset handling, the copy-route flags (0x138 + sRGB), the HDR-route flags (0x39), context rebuilds, the refusal when no 4.x is offered, and threading.

## Task 1: Jitter cycle follows the upscale ratio for `fsr4` (C1)

AMD's FSR 4 doc (`super-resolution-ml.md`, jitter table) asks for `ceil(8 · ratio²)` phases: 18 for 1.5x, 32 for 2x, 15 at SS 0.75. Today only XeSS gets that; every other engine runs 8.

**Scope (David, 2026-11-09):** `fsr4` only. Every jitter site already branches per engine, so TAA, DLSS, XeSS and `fsr` keep today's numbers. `fsr` (FSR 3.1, Sean's) has the same AMD guidance; offer it to Sean as a separate PR item, not in this change.

**Files:** `src/common/temporal_math.h` (`temporalXessJitterPhases` at :105), `src/d3d11/flat_runtime.cpp:4573-4598`, `src/d3d11/native_temporal.cpp:398-410` (VR `jitterCycleFor`), rig `tools/flat_temporal_test/`. `flat_mono_resolve.cpp:526` and `:1081` are XeSS-only refusals and stay as they are.

- [ ] Rig cases first:
  - the helper returns 32 for 2560x720→5120x1440, 15 for 3840x1080→5120x1440, 18 for 1.5x, and `configured` at 1.0.
  - the flat policy gives the ratio cycle for `Fsr4`, and today's numbers for every other engine: XeSS its ratio cycle, everything else 8. Write these zero-change cases before the change and watch them pass on the old code.
  - VR: an FSR 4 eye that upscales gets the ratio cycle. An FSR 3.1 eye gets 8. In VR FSR 4 is distinguished by `kTemporalFlagFsr4` (bit 9), not by the engine enum alone.
- [ ] Keep the helper's name (no XeSS lines touched). Call it from the FSR 4 branch too, with a comment that the formula is AMD's as well.
- [ ] It applies only on the Upstream camera route. `flat_camera_phase.h:209` keeps Legacy and Off at 8 (the ±7/16 lighting-patch bound). Keep that, and make the log say which applied.
- [ ] Flight: SS 0.5 and 0.75. The log shows 32 and 15; captures compared with Flight A.
- [ ] Commit: "FSR 4: jitter cycle follows the upscale ratio".

## Task 3: Camera planes in natural order (C4)

`fsr4CameraPlanes` (`fsr4_version.h:337-354`) passes `cameraNear = FLT_MAX` and `cameraFar = near`. AMD's sample passes `near` and `FLT_MAX`. AMD's FSR 4 debug checker warns for this case: "FFX_FSR_ENABLE_DEPTH_INFINITE and FFX_FSR_ENABLE_DEPTH_INVERTED present, cameraFar value is very low which may result in depth separation artifacting" (`super-resolution-ml.md:335`). FSR 3.1 min/maxes the two, so route 1 never showed it. FSR 4's provider is closed.

- [ ] Rig: change `fsr4_engine_test.cpp:284-291` to expect `near`, `FLT_MAX` (infinite) and `near`, `far` (finite). Watch it fail.
- [ ] Fix `fsr4CameraPlanes` and its comment.
- [ ] Flight: debug view (Task 2) and captures at a station with depth edges. Confirm the checker warning is gone (`ED_FSR4_DEBUG_CHECKER`).
- [ ] Commit: "FSR 4: camera planes in AMD's order".

## Task 4: Fixed exposure on the flat HDR route (C3)

## Task 5: FSR 4 and ED-UP's rejection mask (C2), David's decision after Flight A

FSR 3.1 receives `g.rejection` as its reactive mask (`flat_mono_resolve.cpp:1418-1421`). FSR 4 receives nothing (`fsr4_engine.cpp:1384-1385`). The shared finish (`flat_mono_shader_source.h:668-681`, `701-716`) then replaces the backend's output with a bilinear sample of the raw jittered input wherever the mask is set. That rule was written for DLSS presets that ignore NGX's mask.

Options:
- (a) pass the mask to FSR 4 as `reactive`: a fifth shared R8_UNORM texture. AMD suggests clamping reactive to about 0.9.
- (b) for `fsr4`, skip the raw substitution in the finish.
- (a)+(b) together, the FSR 4-native shape.

- [ ] David chooses from Flight A's refusal-view measurement.
- [ ] Rig cases for the chosen shape. Implement.
- [ ] Flight: SS 0.5 cockpit and on foot, against Flight A.
- [ ] Commit. Option (b) changes the shared finish's contract: a separate commit, named in the PR body.

## Task 6: Quality row (from the 4.1.2 plan's Phase 3; design D4 and D5)

Render size on flat is Elite's Supersampling, and in VR its HMD Image Quality. ED-UP reads it and does not set it. The quality row picks it. Everything else follows the measured ratio: the jitter cycle from Task 1 and the mip bias from Task 7. A user who changes Supersampling in Elite's own menu still gets the right cycle.

Surface: an F8 choice row on the Performance page, cycled with the arrows like the Anti-aliasing row (`menu.cpp` `choicesOf`), generated from an `edvr.ini` `# ui:` line, so it also appears in the installer's settings window.

- `fix.fsr4_quality = native | quality | balanced | performance | ultra` (default `native`).
- Maps to Supersampling 1.0 / 0.67 / 0.59 / 0.5 / 0.33 (AMD's ratios 1.0, 1.5, 1.7, 2.0, 3.0).
- The row dims unless `temporal_aa` is `fsr4` (or `fsr`, if Sean wants it for both).
- Elite reads its settings at launch, so the row is marked `restart`. Its hint names the Supersampling value it will set.

Writing Elite's settings is Sean's decision (D4). Build it behind `advanced.fsr4_write_game_settings = off`. With the key off, the row's hint tells the user which Supersampling to set in Elite.

- [ ] Check that Elite accepts the in-between values (0.67, 0.59, 0.33) in `Custom.<major>.<minor>.fxcfg` and renders at them, or whether its menu's discrete steps are the only usable ones. If only the steps work, map the modes to the nearest step and name the actual ratio in the hint.
- [ ] Writer (old Task 3.1): `eliteGraphicsWriteSupersampling` / restore in `src/d3d11/flat_elite_settings.h`.
  - It refuses a non-Custom preset, backs the file up once, rewrites only `<SSAAMultiplier>` and keeps the line endings.
  - Rig fixtures from a real `Custom.4.4.fxcfg` with no account fields.
  - Six cases: writes only the multiplier, refuses non-Custom, refuses missing, backup once, byte-identical restore, CRLF kept.
- [ ] Keys and row (old Task 3.2): `gen_settings_schema.py --self-test` and `check_config_contract.py` fail first on the new `[fix]` key without its `# ui:` line, then pass.
- [ ] Surfaces (old Task 3.3): F8 row and dim rule; installer preview under Proton lists it.
- [ ] VR: the same row maps to HMD Image Quality by the same ratios. The flight waits for the Quest.
- [ ] Flight: choose Quality, restart; the price line shows the 0.67 render size and the jitter cycle 18. Choose Native, restart; the original size is back. Restore leaves the fxcfg byte-identical.
- [ ] Commits: the writer; the key and row.

## Task 7: Mip bias follows the flat upscale ratio (P4)

AMD recommends `log2(render/display) - 1`: -1.42 at SS 0.75, -2.0 at 0.5. `advanced.texture_lod_bias = auto` derives only from VR's `HMDRenderTargetMultiplier` (`device_hook.cpp:2367-2420`). On flat the Supersampling value is read for reporting only. Every upscaler on flat below 1.0 gets softer textures. Samplers are immutable after creation, so the bias is set when they are created and changes take effect on restart.

- [ ] Rig: `auto` gives -2.0 for flat SS 0.5 and 0 for SS 1.0 with no upscaler.
